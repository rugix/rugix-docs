# Layers

Layers are defined by _layer configuration files_ `<layer name>.toml` in the `layers` directory. As described in the [introduction](/docs/bakery/next/layers), a layer is built by executing recipes. For a given layer, the respective layer configuration file specifies the recipes to be executed as well as an optional parent layer that should be used as a base. Here is an example taken from the [Debian template](https://github.com/rugix/rugix-bakery/tree/main/container/templates/debian-grub-efi):

```toml title="layers/customized.toml"
#:schema https://raw.githubusercontent.com/rugix/rugix/refs/tags/v0.8.0/schemas/rugix-bakery-layer.schema.json

parent = "core/debian-bookworm"

recipes = [
    # Setup Debian for booting via Grub.
    "core/debian-grub-setup",
    # Set a static hostname.
    "core/set-hostname",
    # Persist `/root`.
    "core/persist-root-home",
    # Setup and enable SSH.
    "core/ssh",
    # Enable discovery of the system in the local network.
    "rugix-extra/avahi",
    # Setup the network.
    "setup-network",
    # Install a static website.
    "hello-world",
]
```

This file defines a layer, named `customized`, that is based on the layer `core/debian-bookworm`, a general-purpose layer to build Debian-based systems shipped with Rugix Bakery. The configuration file then specifies a bunch of recipes to set up and customize the system, for instance, setting up a bootloader integration with Grub and providing a network configuration.

In addition to project-specific layers and recipes defined in the project directory, you can use layers and recipes provided by [repositories](/docs/bakery/next/repositories). In case of the example, these repositories are `core` and `rugix-extra`. We will explain repositories in detail later. The built-in
[core layer reference](/docs/bakery/next/reference/core/layers/) lists available
base layers, their architecture variants, source images, and configured recipes.

## Root Layers

If you do not want to use a parent layer, you can also start from scratch by omitting the `parent` setting and specifying `root = true`. For example, here is a layer configuration that bootstraps Debian using the `core/debian-bootstrap` recipe:

```toml title="reproducible-debian.toml"
#:schema https://raw.githubusercontent.com/rugix/rugix/refs/tags/v0.8.0/schemas/rugix-bakery-layer.schema.json

root = true

recipes = [
    "core/debian-bootstrap",
]

[parameters."core/debian-bootstrap"]
suite = "bookworm"
snapshot = "20240501T024440Z"
```

By setting the `snapshot` parameter of the `core/debian-bootstrap` recipe (more on parameters [later](/docs/bakery/next/recipes)), the resulting layer will be based on a particular [Debian snapshot](https://snapshot.debian.org/), thereby leading to a semi-reproducible[^1] build.

## Importing Layers

Rugix Bakery can import layers from external sources. To this end, you can specify a URL.

Here is an example for importing a layer from a Raspberry Pi OS (Bookworm) image:

```toml title="raspios-bookworm.toml"
#:schema https://raw.githubusercontent.com/rugix/rugix/refs/tags/v0.8.0/schemas/rugix-bakery-layer.schema.json

name = "Raspberry Pi OS (Bookworm)"
url = "https://downloads.raspberrypi.com/raspios_lite_arm64/images/raspios_lite_arm64-2024-03-15/2024-03-15-raspios-bookworm-arm64-lite.img.xz"
```

Rugix Bakery can download images and TAR archives from HTTP URLs and create layers from them. This is useful if one wants to take an existing system image as a basis, e.g., when building a customized variant of Raspberry Pi OS. In addition to HTTP URLs, file URLs starting with `file://` are also supported. These URLs are resolved relative to the project directory.

:::tip
You can use this to import a root filesystem built with an external tool, e.g., [Buildroot](https://buildroot.org/) or [Yocto](https://www.yoctoproject.org/).
:::

Note that imported layers must not specify any recipes. Customizations are applied by using them as a parent.

## Excluding Recipes

Recipes may depend on other recipes and as such will pull in their dependencies automatically when specified in the `recipes` list of a layer. To avoid that, e.g., when you want to replace some recipe with a local variant, you can exclude certain recipes from a layer. To this end, you can provide a list of recipes to exclude via the `exclude` property.

## Recipe Artifact Inputs

A recipe can install artifacts produced by a [build rule](/docs/bakery/next/build-rules), such as
an application compiled in a tooling environment. The recipe declares named
inputs. The layer can bind each input to an artifact, and recipes can also supply
[default bindings and their own prerequisite rules](/docs/bakery/next/recipes#artifact-inputs).
For example:

```toml title="recipes/install-app/recipe.toml"
[inputs]
application = "file"
```

A `run` or `install` step reads those inputs through `RECIPE_INPUTS_DIR`:

```sh title="recipes/install-app/steps/00-run.sh"
#!/bin/sh
set -eu
install -D -m 0755 "$RECIPE_INPUTS_DIR/application" "$RUGIX_ROOT_DIR/usr/bin/application"
```

The layer defines the prerequisite rule and connects its output to the recipe:

```toml title="layers/device.toml"
parent = "core/debian-bookworm"
recipes = ["install-app"]

[rules.application]
uses = "vendor/build-app"
inputs.source = { file = "application" }
parameters.architecture = { parameter = "architecture" }

[inputs.install-app]
application = { rule = { node = "application", output = "binary" } }
```

Here, `vendor/build-app` declares a `source` directory input and an `architecture`
parameter, and exports a `binary` file. The `application` source directory is
relative to the repository containing the layer. Bakery supplies the layer's
target architecture as the `architecture` parameter available to its prerequisite
rules.

Layers, prerequisite rules, and image assembly run in one dependency graph.
Bakery builds prerequisite artifacts before running the layer's recipes.
Recipe inputs are read-only and isolated per recipe. Their contents and metadata
participate in layer caching. Bindings apply to recipes executed by this layer;
a parent builds its own inputs and recipes separately.

The `inputs` table uses recipe references as keys, just like `parameters`.
For a repository recipe, use a table such as `[inputs."vendor/install-app"]`.
Recipes accept file and directory inputs. Missing bindings, unknown inputs,
inactive recipes, and incompatible kinds fail before execution.

Bindings support the same file, rule output, selection, and tree forms as
[rule inputs](/docs/bakery/next/build-rules#bind-inputs-and-secrets). An omitted binding forwards
an available enclosing input of the same name, then falls back to a recipe's
`input-defaults` binding. Explicit layer bindings take precedence over both.
Rules defined by a layer can
also consume its parent's `rootfs`, `boot`, `config`, `artifacts`, and `bsp`
directory artifacts through `{ input = "rootfs" }`, for example. A root layer
has no parent artifacts. Cycles between layers and rules are rejected.

Mixins support the same `rules` and `inputs` tables. Their parent artifacts
come from the preceding layer or mixin. See the
[layer input example](https://github.com/rugix/rugix-bakery/tree/main/examples/layer-inputs)
for a complete application-to-filesystem build.

## Inspect and Document Definitions

Discover definitions without building them:

```shell
./run-bakery layers list
./run-bakery layers inspect core/debian-trixie --json
```

Inspection shows the selected definition and its documentation. Add `--json` to export their metadata and adjacent
Markdown. See [definition catalogs](/docs/bakery/next/definition-catalogs/) for
the shared documentation format and reference generator.
