Rugix Ctrl and RAUC install system updates on embedded Linux devices. Both support _dynamic delta updates_, which reduce downloads by reusing data that is already on a device. Downloading only the missing data saves bandwidth, but it can still take a long time when an installer sends thousands of small HTTP requests one after another.

Rugix Ctrl 1.4 introduces a concurrent fetching pipeline that removes most of this waiting. In our benchmarks with 40 ms of added round-trip latency, median installation speedups ranged from about **14× to 31× compared with Rugix Ctrl 1.3.0 and RAUC 1.15.2**. Across three Debian update scenarios at 10 ms of added round-trip latency, Rugix Ctrl also transferred **25.5–28.5% fewer bytes than RAUC**, counting traffic in both directions.

In this article, we explain where the time goes during dynamic delta updates, present our measurements of installation time and network traffic, and discuss the limits of these results.

## Where the Time Goes

For dynamic delta updates, an update bundle carries a _block index_ for each payload. The index lists the hashes of the chunks that make up the new version, for example, of a filesystem image. The device compares these hashes with the chunks it already has, for example, in the currently installed system, and fetches only the missing chunks from the complete bundle. An ordinary HTTP server can host the bundle, as long as it supports byte-range requests, which let a client download a specific part of a file. Our earlier article, [Efficient Delta Updates](/blog/efficient-delta-updates), explains how this approach reduces downloads and compares it with other delta update techniques.

The missing chunks are rarely contiguous, so downloading them can require thousands of small requests. Each request waits at least one network round trip for its response, and each new connection adds further round trips. Rugix Ctrl 1.3.0 sent its range requests one after another and frequently opened new connections, so the waiting grew with every request. On a link with noticeable latency, most of the installation time went into waiting instead of transferring data.

Rugix Ctrl 1.4 reduces both the number of requests and the time spent waiting for them. It combines adjacent missing chunks into larger ranges, reuses connections, and keeps several requests in flight at once. Downloads continue while the installer verifies, decompresses, and writes the data it has already received. These improvements are enabled by default and work with existing bundles that include block indices.

## Faster Installations

We compared Rugix Ctrl 1.3.0, the new fetcher, and RAUC 1.15.2 using three Debian update scenarios: a monthly Bookworm update, an annual Bookworm update, and an upgrade from Bullseye to Bookworm. RAUC calls its dynamic delta mechanism _adaptive updates_. In all three scenarios, each installer reconstructed the same 1.38 GiB filesystem image, starting from a different source image per scenario.

We limited the link between the update server and the device to **20 MiB/s** and added **0, 10, or 40 ms of round-trip latency**. We repeated every measurement five times. For the monthly update at 40 ms added latency, median installation times were **457.6 seconds with Rugix Ctrl 1.3.0**, **440.5 seconds with RAUC**, and **31.0 seconds with the new fetcher**.

The request and connection counts show where this difference comes from. For the monthly update at 10 ms added latency, Rugix Ctrl 1.3.0 opened a new connection for each of its 2,750 requests. The new fetcher combined the missing chunks into 931 requests over **four connections**. RAUC reused 16 connections but issued 9,932 requests, and its installation times grew with latency much like those of Rugix Ctrl 1.3.0.

Across all three scenarios at 40 ms added latency, median speedups were about **15–31× over Rugix Ctrl 1.3.0 and 14–31× over RAUC**. We computed each speedup by dividing a baseline installation time by the new fetcher's time from the same repetition and then took the median of the five ratios. At 10 ms added latency, speedups over the two baselines ranged from about seven to eleven times. At zero added latency, we found no consistent improvement over Rugix Ctrl 1.3.0. The pipeline helps most when an installer would otherwise wait for sequential network requests.

## Less Network Traffic Than RAUC

Metered connections typically count all traffic in both directions, not only the update data itself. We therefore measured the actual traffic on the device's network interface, including response data, protocol overhead, requests, acknowledgments, and retransmissions. Packet captures and Linux interface counters agree for every accepted run.

<PlotDownloadSizes client:visible />

For the monthly update at 10 ms added latency, the new Rugix Ctrl fetcher transferred **175.9 MiB**, compared with **246.1 MiB for RAUC**. Across the three selected scenarios, Rugix Ctrl used about **25.5–28.5% less interface traffic**.

The two systems split and compress data differently. RAUC identifies reusable data in fixed 4 KiB blocks and compresses groups of blocks together in its bundle, so fetching one missing block can require downloading the adjacent data in its group. Rugix Ctrl uses content-defined chunks, whose boundaries follow the data instead of fixed offsets, and compresses each chunk individually. These choices affect both how much data a device can reuse and how much compressed data it must fetch.

The measured download sizes also informed an update to our [delta update savings calculator](/blog/efficient-delta-updates#savings-calculator). Its [calibration report](https://github.com/rugix/rugix-benchmarks/blob/main/benchmarks/dynamic-downloads/results/2026-10/calculator.md) explains how the measurements relate to the models of our earlier article.

## Benchmark Setup and Limits

We measured the fetching change at prerelease revision [`b82749f`](https://github.com/rugix/rugix/commit/b82749ff34ee8668fb3e53322af039a083e8bf69), labeled “Rugix Ctrl 1.4 Fetcher” in the results. These measurements cover that change rather than a fresh benchmark of the final release.

The tests ran in fresh x86-64 KVM guests with four virtual CPUs, 8 GiB of RAM, and blank target slots. The installers wrote the Debian filesystem images to the target slots as data, and the installed systems were not booted. Before timing, we prepared the block indices of the source images and warmed the caches. The measured times therefore exclude booting, initial index generation, and rebooting. Every run passed an independent check of the reconstructed image.

Rugix Ctrl used Casync chunks with a nominal size of 64 KiB and XZ compression. RAUC used its built-in `block-hash-index` method and 64 KiB XZ compression groups, following its [adaptive update documentation](https://rauc.readthedocs.io/en/latest/advanced.html#block-based-adaptive-update-block-hash-index). We rebuilt both Rugix Ctrl versions with the same pinned compiler and used the new fetcher's default settings. We also checked RAUC with HTTP/2 over TLS, which did not substantially change its installation times in these measurements.

These results describe selected update pairs in a controlled environment. Embedded CPUs, flash storage, cold caches, and different networks can change installation times. The [benchmark suite](https://github.com/rugix/rugix-benchmarks/tree/main/benchmarks/dynamic-downloads) contains the reproducible setup, all individual measurements, and the complete HTTP/2 results.

## Try It with Your Own Images

The fetching improvements are included in [Rugix Ctrl 1.4](/blog/releases/1.4) and work with any HTTP server that supports byte-range requests. See the [Rugix Ctrl documentation](/docs/ctrl) to get started, or run the [benchmark suite](https://github.com/rugix/rugix-benchmarks/tree/main/benchmarks/dynamic-downloads) with your own images.
