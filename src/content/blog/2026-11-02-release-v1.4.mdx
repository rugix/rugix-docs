We are excited to announce the release of Rugix Ctrl 1.4. 🎉

Rugix Ctrl 1.4 prepares installed systems for dynamic delta updates automatically and makes those updates much faster on networks with latency. For Rugix Apps, the release adds versioned configuration, staged deployments, and a shared store that keeps identical data only once across application versions. It also makes device initialization recoverable after interruptions and adds a Nix integration for building bundles and configuring Rugix Ctrl.

## Automatic Slot Indices and Faster Delta Updates

Dynamic delta updates reduce downloads by reusing data that is already on a device. To find reusable data, Rugix Ctrl compares the _block index_ of an update, a list of hashes of the chunks that make up the new version, with the chunks available locally. For this comparison, Rugix Ctrl needs a matching index for the data in each _slot_, the partition or file that holds a part of the installed system, such as its root filesystem.

Rugix Ctrl 1.4 now retains the verified block indices that regular slot payloads supply. Once a device has installed an update from a bundle with block indices, subsequent HTTP updates download only the missing chunks, provided that the server supports byte-range requests. Update bundles built with Rugix Bakery include block indices by default. Slots written from a static delta patch do not receive an index.

Data installed at the factory usually has no matching index yet. If you want the first update to reuse that data, enable `install.auto-index`. Rugix Ctrl then computes missing indices for existing slots as needed during a full system update. This option is disabled by default. See [Delta Updates](/docs/ctrl/updates/delta-updates#slot-indices) for the configuration and requirements.

Rugix Ctrl 1.4 also fetches missing data much more efficiently. It combines adjacent missing chunks into larger HTTP ranges, reuses connections, and keeps several requests in flight while the installer verifies, decompresses, and writes the data it has already received. Interrupted transfers now resume with bounded retries. These improvements are enabled by default and work with existing bundles that include block indices.

In our benchmark of a monthly Debian update with 40 ms of added round-trip latency, the new fetcher reduced the median installation time from **457.6 seconds to 31.0 seconds** compared with Rugix Ctrl 1.3.0. Read [Faster Delta Updates](/blog/faster-delta-updates) for the complete comparison with Rugix Ctrl 1.3.0 and RAUC, including the benchmark setup and its limits.

## Application Configuration and Staged Deployments

[Rugix Apps](/blog/2026-03-23-rugix-apps) manages application workloads independently of the base system. It installs each application version as an immutable _generation_ and can roll back to a previous generation when an update does not work as expected.

Devices running the same generation often need different settings, for example, the address of a site-specific server. Rugix Ctrl 1.4 adds device-specific JSON configuration, which it manages separately from the immutable generations. An app bundle can include a JSON Schema and default settings, and Rugix Ctrl validates the resulting configuration before activating the workload.

Configuration has its own revision history. When an app rolls back, Rugix Ctrl restores the configuration revision that the older generation was last activated with. If the schema of a new generation no longer accepts the current configuration, supply a new document with `--config` when installing or activating that generation. Applying the document that an app already runs with no longer restarts its workload.

You can now also separate installation from activation. For example, you can download and install an update while the current workload keeps running and then activate it during a maintenance window:

```shell
rugix-ctrl apps install --bundle-hash HASH --no-activate my-app-v2.rugixb
rugix-ctrl apps activate my-app 2 --config config.json
```

Here, `HASH` is the bundle hash produced by Rugix Bundler, `my-app` is the app ID, and `2` is the generation number reported by the installation. For signed bundles, Rugix Ctrl verifies the signature against the configured root certificates instead, so you can omit `--bundle-hash`. Garbage collection keeps a staged generation until it or a newer generation is activated.

Management tools can attach a JSON document with `--origin` to record the release or deployment that produced a generation, so that they can later recognize the generations they installed. See [Application Management](/docs/ctrl/application-management/) and [Application Configuration](/docs/ctrl/application-management/configuration) for the complete workflows. Rugix Apps remains experimental, so its interfaces may change between releases.

## Shared Storage for Application Data

Keeping several generations of a container workload can consume substantial storage, even when most of their contents are identical. Rugix Ctrl 1.4 adds a _content-addressed store_, a storage area shared across apps and generations. The store splits files into chunks, keeps each distinct chunk only once, and stores the chunks compressed as the bundle delivered them.

Docker Compose app bundles packed with Rugix Bundler now keep their container images in this store by default, instead of as files in the generation directory. When activating a generation, Rugix Ctrl streams the images from the store into Docker. When deactivating it, Rugix Ctrl removes the Rugix-owned image tags, so images of old generations no longer accumulate in Docker. Retained generations keep their stored data for later activation or rollback, and garbage collection releases data once no generation references it.

Chunks in the store also serve as local data sources when installing app and system bundles, which gives dynamic delta updates more data to reuse.

Because stored files no longer appear in the generation directory, use `rugix-ctrl apps files` and `rugix-ctrl apps cat` to list and read the files of a generation, wherever they are kept. The new `rugix-ctrl store` commands inspect, verify, and garbage-collect the store. See the [store reference](/docs/ctrl/reference/store) for details.

## Recoverable Device Initialization

When a device boots for the first time, Rugix Ctrl can _bootstrap_ it, for example, by growing the partition table and creating the data partition. Rugix Ctrl 1.4 records partition creation and filesystem initialization in a durable journal. If bootstrapping is interrupted, for example, by a power failure, the next boot resumes from that journal and preserves filesystems whose completion was recorded durably. If the disk, the bootstrapping configuration, or the planned partition geometry changed in the meantime, Rugix Ctrl rejects recovery instead of applying an outdated plan to the device.

On Raspberry Pi, the `rpi-tryboot` and `rpi-uboot` boot flows now preserve the contents of a prepared boot partition when `boot.img` is present, so authenticated boot images remain unchanged.

## Bundle Inspection and Nix Integration

The new `rugix-ctrl bundle inspect` command reads a bundle from a file, an HTTP(S) URL, or standard input and reports its manifest and payload metadata.

For Nix users, the Rugix flake now provides `lib.mkBundle` and `lib.mkComposeBundle` for building Rugix bundles and Docker Compose app bundles in Nix. It also provides a NixOS module that sets up the Rugix Ctrl services, the daemon configuration, and app recovery. See the [Nix integration guide](https://github.com/rugix/rugix/blob/v1.4.0/nix/README.md).

## Upgrading to 1.4

Before deploying Rugix Ctrl 1.4, check the following changes:

- **HTTPS uses the operating system's trust store.** Rugix Ctrl now verifies HTTPS update servers against the operating system's CA certificates and no longer embeds a separate set of public CA certificates. Install and maintain `ca-certificates` on target devices. Bundle signing roots remain configured independently.
- **Compose images use the store by default.** Older Rugix Ctrl versions cannot read stored files. If a device rolls back to a system with an older Rugix Ctrl version, a generation installed with stored images can only activate while Docker still has those images, and custom orchestrator scripts that call `rugix-ctrl apps cat` fail. While devices may still roll back to an older Rugix Ctrl version, pack Compose bundles with `--image-location file` to keep the images as files in the generation directory.
- **Application inspection output changes.** `rugix-ctrl apps info` now reports the persisted lifecycle state as `lifecycle` instead of `state`, alongside the live workload `status`. It also omits `createdAt` when generation metadata is missing. Update tools that consume this output.
- **Each app bundle targets one app.** Rugix Bundler and Rugix Ctrl reject app bundles with payloads for several apps. No packing command produces such bundles, so this only affects hand-written manifests. Pack a separate bundle for each app.

The [changelog](https://github.com/rugix/rugix/blob/v1.4.0/CHANGELOG.md) lists all changes, including the security fixes from the 1.3 patch releases.
