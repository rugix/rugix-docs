We are excited to announce the release of Rugix Ctrl 1.4. 🎉

Rugix Ctrl 1.4 makes delta updates much faster, especially on networks where each request adds a noticeable wait. For Rugix Apps, the release adds device-specific settings that roll back together with app versions, lets you download an update now and start it later, and stores data shared between app versions only once. It also lets bootstrapping recover from interruptions and adds a Nix integration for building bundles and configuring Rugix Ctrl.

## Faster Delta Updates

Delta updates reduce downloads by reusing data that is already installed on a device. Rugix Ctrl 1.4 downloads the missing parts much faster by combining small requests, reusing connections, and downloading several parts at once. This reduces the time spent waiting for the update server, especially on connections with noticeable delays. Interrupted transfers now resume automatically. These improvements are enabled by default and work with existing bundles that support delta updates.

In our benchmark of a monthly Debian update with 40 ms of added round-trip latency, an early build of Rugix Ctrl 1.4 reduced the median installation time from **457.6 seconds to 31.0 seconds** compared with Rugix Ctrl 1.3.0. Read [Faster Delta Updates](/blog/faster-delta-updates) for the complete comparison with Rugix Ctrl 1.3.0 and RAUC, including the benchmark setup and its limits.

Delta updates now also happen by default on subsequent updates. After installing a regular system update, Rugix Ctrl keeps a record of the installed data so it can recognize and reuse it next time. This requires bundles with the necessary information, which Rugix Bakery includes by default, and an HTTP server that supports downloading individual parts of a bundle. Reusing factory-installed data without that record remains opt-in through `install.auto-index`; see [Delta Updates](/docs/ctrl/updates/delta-updates#slot-indices) for the requirements and configuration.

## Application Settings and Staged Updates

[Rugix Apps](/blog/2026-03-23-rugix-apps) manages applications independently of the base system. Rugix Ctrl keeps earlier versions of an app on the device, so it can roll back when an update does not work as expected.

Devices running the same app version often need different settings, for example, the address of a site-specific server. Rugix Ctrl 1.4 lets you give each device its own settings as a JSON document, which it keeps separately from the app versions. An app bundle can include default settings and a JSON Schema describing valid settings, and Rugix Ctrl checks a device's settings against the schema before starting the app. Applying the settings that an app already runs with does not restart it, so management tools can safely apply their desired settings again and again.

Rugix Ctrl also remembers which settings each app version ran with. When an app rolls back, Rugix Ctrl restores the settings used with the earlier version, so settings written for a newer version cannot break the older one. If a new app version no longer accepts a device's current settings, the update stops before the running app is touched, and you can supply new settings with the update using `--config`.

You can now also download an update now and start it later. For example, a device can download and install a new version of an app while the current version keeps running and then switch to it during a maintenance window. Cleanup of old app versions does not remove a downloaded version before you start it or a newer one. Management tools can also record which release or deployment installed an app version, so that they can later recognize the versions they installed.

See [Application Management](/docs/ctrl/application-management/) and [Application Configuration](/docs/ctrl/application-management/configuration) for the complete workflows. Rugix Apps remains experimental, so its interfaces may change between releases.

## Shared Storage for Application Data

Keeping earlier app versions for rollback can take substantial storage, especially for container images, even though consecutive versions usually share most of their contents. Rugix Ctrl 1.4 adds a store that keeps this shared data only once. Retaining an earlier version therefore needs little additional space beyond the data that changed.

Docker Compose apps packed with Rugix Bundler now keep their container images in the store by default. Rugix Ctrl loads the images into Docker when needed and keeps the stored copies available for a later rollback. It frees stored data once no retained version needs it.

The store also benefits future updates. When installing app or system bundles over HTTP, Rugix Ctrl reuses data from the store instead of downloading it again. See the [store reference](/docs/ctrl/reference/store) for details.

## Recoverable Bootstrapping

When a device boots for the first time, Rugix Ctrl can _bootstrap_ it, for example, by growing the partition table and creating the data partition. If bootstrapping is interrupted, for example, by a power failure, Rugix Ctrl 1.4 can resume it on the next boot from its recorded progress. Filesystems whose completion Rugix Ctrl had recorded are kept as they are. Before resuming, Rugix Ctrl verifies that the disk and the bootstrapping configuration still match the interrupted run. If they do not, it refuses to resume, preventing an outdated plan from being applied to a changed device. See [Interrupted Bootstrapping](/docs/ctrl/state-management/bootstrapping#interrupted-bootstrapping) for what recovery covers, including how to make bootstrapping hooks safe to run again.

## Further Improvements

The new `rugix-ctrl bundle inspect` command shows what an update bundle declares, helping you review it before installation. See [Inspecting a Bundle](/docs/ctrl/updates/update-bundles#inspecting-a-bundle) for details.

For Nix users, the Rugix flake can now build Rugix bundles and Docker Compose app bundles in Nix. It also provides a NixOS module that configures Rugix Ctrl, its daemon, and app recovery. See the [Nix integration guide](https://github.com/rugix/rugix/blob/v1.4.0/nix/README.md).

On Raspberry Pi, system updates with the `rpi-tryboot` and `rpi-uboot` boot flows now keep the contents of a prepared boot partition when it contains a `boot.img`, so authenticated boot images remain unchanged.

## Upgrading to 1.4

Before deploying Rugix Ctrl 1.4, check the following changes:

- **HTTPS uses the operating system's trust store.** Rugix Ctrl now verifies HTTPS update servers against the operating system's CA certificates and no longer embeds a separate set of public CA certificates. Install and maintain `ca-certificates` on target devices. Bundle signing roots remain configured independently.
- **Compose images use the store by default.** Stored images no longer appear as files in the installation directory of an app version. Tools that read them must use `rugix-ctrl apps cat` instead. Older Rugix Ctrl versions cannot read data kept in the store. If a device rolls back to a system with an older Rugix Ctrl version, an app version installed with stored images can only start while Docker still has those images, and custom orchestrator scripts that call `rugix-ctrl apps cat` fail. While devices may still roll back to an older Rugix Ctrl version, pack Compose bundles with `--image-location file` to keep the images as regular files.
- **Application inspection output changes.** `rugix-ctrl apps info` now reports the recorded lifecycle state of an app as `lifecycle` instead of `state`, alongside the current `status` of its workload. It also omits `createdAt` for app versions whose metadata is missing. Update tools that consume this output.
- **Each app bundle targets one app.** Rugix Bundler and Rugix Ctrl reject app bundles with payloads for several apps. No packing command produces such bundles, so this only affects hand-written manifests. Pack a separate bundle for each app.

The [changelog](https://github.com/rugix/rugix/blob/v1.4.0/CHANGELOG.md) lists all changes, including the security fixes from the 1.3 patch releases.
