Rugix Ctrl and RAUC install system updates on embedded Linux devices. Both support dynamic delta updates, which reduce downloads by reusing data already on a device. Our earlier article, [Efficient Delta Updates](/blog/efficient-delta-updates), compared techniques for reducing those downloads.

**Rugix Ctrl 1.4 introduces a concurrent fetching pipeline that makes these updates much faster over HTTP.** In our benchmarks at 40 ms of added round-trip delay, median installation speedups ranged from **about 14× to 31× compared with Rugix Ctrl 1.3.0 and RAUC 1.15.2**.

Across three Debian update scenarios at 10 ms added round-trip delay, Rugix Ctrl transferred **25.5–28.5% fewer bytes than RAUC**, counting traffic in both directions.

## Fewer Bytes, Less Waiting

With _dynamic delta updates_, a device reuses parts of its existing system and downloads the missing data from a complete update bundle. RAUC supports the same approach under the name _adaptive updates_. An ordinary HTTP server can host that bundle. It only needs to support byte-range requests, which let an installer fetch selected parts of a file.

This can avoid downloading most of an image, but it can also require thousands of small requests. If those requests happen sequentially, each one pays the network round-trip cost. Opening a new connection for each request adds further overhead.

Rugix Ctrl 1.3.0 [fetched ranges sequentially](https://github.com/rugix/rugix/issues/136) and frequently opened new connections. Rugix Ctrl 1.4 combines adjacent missing blocks into larger ranges, reuses connections, and fetches several ranges concurrently. Downloads can progress while the installer verifies, decompresses, and writes data it has already received.

In our monthly update benchmark, the new fetcher used **four connections instead of 2,750**. These improvements are enabled by default and work with existing block-encoded bundles, which divide payloads into individually retrievable blocks.

## Faster Installations

We compared Rugix Ctrl 1.3.0, the new fetcher, and RAUC 1.15.2 using three Debian update scenarios: a monthly Bookworm update, an annual Bookworm update, and an upgrade from Bullseye to Bookworm. Each installer reconstructed the same 1.38 GiB filesystem image.

The link was limited to **20 MiB/s**, with **0, 10, or 40 ms of added round-trip latency**. Linux traffic-control tools applied the bandwidth limit and packet delays. We repeated every measurement five times.

For the monthly update at 40 ms added latency, median installation times were **457.6 seconds with Rugix Ctrl 1.3.0**, **440.5 seconds with RAUC**, and **31.0 seconds with the new fetcher**. Both baselines took more than seven minutes; the new pipeline completed the update in roughly half a minute.

Rugix Ctrl 1.3.0 and RAUC had similar median installation times at 40 ms across all three scenarios. The new fetcher was about **15 to 31 times faster than Rugix Ctrl 1.3.0 and 14 to 31 times faster than RAUC**. These are median speedups calculated by pairing each baseline run with the new fetcher run from the same repetition.

At 10 ms added latency, speedups over the two baselines ranged from about seven to eleven times. At zero added latency, we found no consistent improvement over Rugix Ctrl 1.3.0. The new pipeline helps most when the installer would otherwise spend time waiting for sequential network requests.

The new fetcher had lower median installation times than RAUC in all three selected scenarios and at all tested latencies. We also checked RAUC with HTTP/2 over TLS; it did not substantially change installation time in these measurements.

## Less Network Traffic Than RAUC

For devices on metered connections, transferred bytes matter alongside installation time. We measured actual traffic on the network interface, including response data, protocol overhead, requests, acknowledgments, and retransmissions. Packet captures and Linux interface counters agree for every accepted run.

<PlotDownloadSizes client:visible />

For the monthly update at 10 ms added latency, the new Rugix Ctrl fetcher transferred **175.9 MiB**, compared with **246.1 MiB for RAUC**. Across the three selected scenarios, Rugix Ctrl used about **25.5–28.5% less interface traffic**.

The two systems use different block layouts. RAUC identifies reusable fixed 4 KiB blocks and fetches data from compressed groups in its bundle. Rugix Ctrl uses content-defined chunks, whose boundaries follow the data, and compresses those chunks individually. These choices affect both reuse and the amount of compressed data that must be fetched.

We also [compared measured download sizes with our earlier models](https://github.com/rugix/rugix-benchmarks/blob/main/benchmarks/dynamic-downloads/results/2026-10/calculator.md) to update the [delta update savings calculator](/blog/efficient-delta-updates#savings-calculator).

## About the Benchmarks

We used fresh x86-64 KVM guests with four virtual CPUs, 8 GiB RAM, and blank target slots. The corpus filesystems were installed as data and were not booted. Reuse indices were prepared and caches warmed before timing; boot, initial index generation, and reboot are excluded. Every run passed an independent check of the reconstructed image.

Rugix Ctrl used Casync chunks with a nominal 64 KiB size and XZ compression. RAUC used its built-in `block-hash-index` method and 64 KiB XZ compression groups, following the example in its [adaptive-update documentation](https://rauc.readthedocs.io/en/latest/advanced.html#block-based-adaptive-update-block-hash-index). Both Rugix Ctrl versions were rebuilt with the same pinned compiler, and we used the new fetcher's default settings.

We measured the fetching change at prerelease revision [`b82749f`](https://github.com/rugix/rugix/commit/b82749ff34ee8668fb3e53322af039a083e8bf69), shown as “Rugix Ctrl 1.4 Fetcher” in the graphs.

These results describe selected update pairs in a controlled environment. Embedded CPUs, flash storage, cold caches, and different networks can change installation times. The [native benchmark suite](https://github.com/rugix/rugix-benchmarks/tree/main/benchmarks/dynamic-downloads) contains the reproducible setup, all individual measurements, and complete HTTP/2 results.
